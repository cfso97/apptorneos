Notas del entorno de desarrollo de Cristian (Windows 11, Git Bash como shell de las tools):

- `pnpm` no está en el PATH de Git Bash directamente, pero sí vía `corepack pnpm <comando>` (corepack 0.35.0 ya instalado). Usar `corepack pnpm install`, `corepack pnpm exec <bin>`, etc.
- Docker Desktop no arranca solo; el daemon (`docker info`) tarda en responder incluso después de lanzar el proceso. Se inicia con `Start-Process 'C:\Users\cfso9\AppData\Local\Programs\DockerDesktop\Docker Desktop.exe'` vía PowerShell (la ruta en `C:\Program Files\Docker\...` no existe en esta máquina). Hay que esperar unos segundos/reintentar `docker info` hasta que responda antes de correr `docker compose up -d`.
- El proyecto ya trae `docker-compose.yml` en la raíz con Postgres (`localhost:5432`, user/password/torneos_saas) y Redis (`localhost:6379`) — normalmente ya están corriendo (contenedores persistentes), conviene chequear con `docker compose up -d` (es idempotente) antes de asumir que hay que crearlos.
- **Bug preexistente corregido en Fase 0:** `apps/backend/.eslintrc.json` apuntaba `parserOptions.project` a `tsconfig.json`, el cual excluye la carpeta `test/` — esto rompía `pnpm lint` en cualquier PR que tocara `test/**/*.ts` (ya rompía desde el commit inicial del monorepo, con `test/app.e2e.spec.ts`). Se arregló agregando `apps/backend/tsconfig.eslint.json` (incluye `src` y `test`, sin excluir `test`) y apuntando `.eslintrc.json` ahí. Si en el futuro el lint vuelve a fallar con "file was not found in any of the provided project(s)" sobre un archivo de `test/`, es la misma causa.
- **`prisma migrate dev` NO funciona en el shell de las tools (Bash tool de Claude Code)** — siempre falla con "Prisma Migrate has detected that the environment is non-interactive", incluso con `--create-only` o con "y" pipeado a stdin (detecta ausencia de TTY real, no de stdin). Workaround verificado (Fase "perfiles reclamables", 2026-09-29): 1) `prisma migrate diff --from-url "<DATABASE_URL sin comillas del .env>" --to-schema-datamodel prisma/schema.prisma --script` genera el SQL exacto que generaría `migrate dev`; 2) crear a mano la carpeta `prisma/migrations/<timestamp UTC `date -u +%Y%m%d%H%M%S`>_<nombre>/migration.sql` con ese SQL; 3) `prisma migrate deploy` (sí es no-interactivo) la aplica y la registra en `_prisma_migrations`. Confirmado que el resultado es indistinguible de una migración generada por `migrate dev` normal.
- **`prisma migrate reset --force` en este proyecto NO corre el seed automáticamente** — falta el bloque `"prisma": { "seed": "ts-node prisma/seed.ts" }` en `apps/backend/package.json` (Prisma solo auto-invoca el seed en `migrate reset`/`migrate dev` si ese bloque existe). Sin eso, un reset deja `plans`/`permissions`/`sports` vacíos y cualquier flujo que dependa de ellos (p.ej. `OrganizationsService.create` con `PLAN_PLACEHOLDER_ID`) falla con violación de FK — causó que toda la suite e2e fallara en cascada hasta diagnosticarlo. Mientras no se agregue ese bloque (cambio de config que le compete decidir a Cristian, no es una migración de esquema), correr `pnpm run prisma:seed` a mano inmediatamente después de cualquier `migrate reset`.
- Al correr `prisma generate`/`migrate` desde las tools mientras el `pnpm dev` (nest --watch) de Cristian está corriendo, falla con `EPERM: operation not permitted, rename ... query_engine-windows.dll.node` porque el proceso de dev tiene el motor de Prisma cargado. Se soluciona parando el proceso node del dev server (`Get-CimInstance Win32_Process -Filter "Name='node.exe'"` vía `powershell -NoProfile -Command` para identificar el PID correcto por `CommandLine`, luego `Stop-Process -Force`) antes de generar/migrar, y volviendo a levantarlo después con `corepack pnpm dev` en background para dejar el entorno como estaba.
